The default figure is the share of the range ("62%"); a `valueText` such as "7/19" replaces it. A missing value or a range with no width shows "—" as `role="img"` "…: no data", because an empty ring would read as zero. A zero draws no arc, since a round cap would paint a dot. - **2026-11-08 · P0c.4 split into P0c.4a (writes) and P0c.4b (reads); P0c.4a done.**
  - **Why split:** keeping another process's writes (P0c.4a) does not make the running server _serve_ them. Each store reads its document once, so after a backfill it keeps serving its held copy until it next writes that document. The restart rule can only go once the stores re-read (P0c.4b).
  - **Mechanism:** optimistic concurrency at the store, one `version` column (`BIGINT NOT NULL DEFAULT 0`, added idempotently by the ensure-schema DDL, so production Supabase gains it on the next boot). A write is a _change_ applied to the latest document, never this process's whole copy.
  - **The retry queue had the same hazard:** a whole document queued through an outage was replayed blind. Now changes are re-applied, and a queued `write` document replays only while the row is at the version this process last read. A document this process never read keeps last-writer-wins replay (no version to check). Only database errors queue: a change that cannot apply would otherwise block every later write.
  - **Other `write` callers** (prediction history, post-mortems, driver availability, power units) still read-modify-write per call, as before; their window is one call long. Moving them to `update` is a candidate follow-up, not done.
  - **For P0c.6:** the migration should copy rows as they are; `version` can start at 0 on the VM.
  - **For P0c.2:** `app/data/store.py` is at 477/500 counted lines; its host classification (P0c.2 adds the self-hosted kind) should move to its own module first.

- **2026-11-09 · P0c.2c done: f1db downloads back off after a failure.** Decisions and findings:
  - **The window:** a failed download (any exception) opens a window of 60 s, doubling per consecutive failure up to 15 min (`F1DB_DOWNLOAD_BACKOFF_SECONDS` / `F1DB_DOWNLOAD_BACKOFF_MAX_SECONDS`, env-overridable like the neighbouring `F1DB_*` settings, which live in `f1db_source.py`, not `app/config.py`); a successful download resets it. No download of any kind starts inside it; with no dataset on disk, `ensure_db` and `sync_to_latest` raise `F1dbUnavailableError` **before the release lookup**, so a refused read makes no request at all. A sync that still has a dataset keeps it and says why ("download failed, kept … : f1db download paused …").
  - **Each of the 637 "downloads" was really two or three requests:** with the file missing, `ensure_db` resolved `target_version()` on every read, so every read also sent the release-page HEAD (and, when that failed, the API GET) before the download.
  - **`F1dbUnavailableError` subclasses `OSError`:** a failed download already is one (`requests` errors are), and readers answer those as "f1db unavailable" (`canonical_names.F1DB_READ_ERRORS`, the `except (…, OSError)` handlers), so a refusal takes exactly that path.
  - **`ensure_db` now fetches a missing file under `_sync_lock`** (the existing lock, which also guards the backoff state), re-checking the file once it holds it. Before, concurrent readers each downloaded at once, all writing the same `f1db.db.incoming` staging path, so one thread could `os.replace` a file another was still writing into. Readers that queue behind an in-flight download get the file when it lands, or the refusal at once if it failed. A file that exists never touches the lock, as before.
  - **One log line per window:** `f1db.download.backoff` (failures, seconds) when a failure opens a window, `f1db.download.refused` once on its first refusal; `tests/conftest.py`'s `_no_local_f1db` resets the backoff for every test.
