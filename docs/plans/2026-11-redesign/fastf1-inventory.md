## 0. How the cap works (fastf1 3.8.3 in `.venv`, verified)

- **Error class:** `fastf1.exceptions.RateLimitExceededError(FastF1CriticalError)`, and `FastF1CriticalError(RuntimeError)` (`fastf1/exceptions.py:70,80`). It is raised by `_CallsPerIntervalLimitRaise` (`fastf1/req.py:64-80`). Every URL matches `"any API: 500 calls/h"` (`req.py:95-99`). The `ergast.com: 200 calls/h` rule (`req.py:88-92`) does **not** match `api.jolpi.ca`, so Jolpica counts only against the 500.
- **What counts:** the limiter sits under requests-cache (`req.py:115`, `CacheMixin` first in the MRO), so a fresh cache hit is free. Every miss counts, and so does every **revalidation**:
  - the schedule (raw.githubusercontent.com) sends `max-age=300`;
  - Jolpica sends `max-age=600` (checked with `curl -I` on 2026-11-14);
  - so with `cache_control=True` (`req.py:252-254`), a "cached" schedule costs 1 request per season every 5 minutes, and a Jolpica URL 1 every 10 minutes.
  - A rejected call is also appended to the window (`req.py:77-80`), so steady traffic keeps the cap shut.
- **Soft errors don't help:** `soft_exceptions` re-raises `FastF1CriticalError` (`fastf1/logger.py:113-115`), so `session.load()` itself raises.
- **stale-if-error:** for a URL that is already cached, an over-cap revalidation is served from the stale copy (requests-cache 1.3.3 `session.py:318-332`). Only uncached URLs raise: cold schedules, new Jolpica URLs, and live timing.
- **Live-timing waste per `session.load()`:** each feed is tried on livetiming.formula1.com (401), then on the mirror (`fastf1/_api.py:1768-1773`), and neither failure is cached. Which feeds are tried depends on the load flags (`fastf1/core.py:1411-1436`):
  - **`laps=False`** (and `messages` left at its default, True): `session_info` + `driver_list` + `race_control_messages` = 3 feeds × 2 = **6 live-timing requests**, plus **1 Jolpica** request for results (none for SQ).
  - **`laps=True`**: **12 (Q) to 16 (R)** live-timing requests, as measured in P0b.10. A race also asks Jolpica for its results and first-lap times (2 requests).
- **Already OpenF1-first:** qualifying (`predictions/openf1_qualifying.py`), the race classification (`race_classification.py:167`), stints (`race_stints.py:261`), stationary pit times (`pit_sheet.py:214`) and telemetry (`openf1/telemetry.py`). However, every OpenF1 reader still finds its session through **FastF1's schedule** (`openf1/sessions.py:95`).

Legend: **Boot** = on the boot/warm-up or prefetch path. LT = failed live-timing requests. J = Jolpica requests. The warm-up steps (`app/services/readiness.py:149-154`: f1db sync, model, f1db schedule, store) make **no** FastF1 calls.

## 2. Inventory: schedule-only reads (`get_event_schedule`)

Each call costs 1 request per season every 5 minutes (a revalidation). Every `fastf1.get_session()` also calls it internally (`fastf1/events.py:118`). The replacement for all of them is the f1db `race` table:

- it holds the **full 2026 calendar** (23 rounds) with every session's date and time in UTC (checked: R19 race `2026-11-01 20:00` = 14:00 local);
- OpenF1 `sessions` covers same-weekend changes.

Two cross-cutting points:

- Ranks 4–10 move traffic onto OpenF1, which sends 429 after about 20 requests in a burst (`openf1/client.py:7`) and has no response cache. That is why D1's read-through Postgres store has to land before or alongside rank 4.
- Several caches keep an empty answer even when the empty answer was a capped failure: A1 `:324`, A6 `:243`, A7 `:289`, A9, A11 `:148`, A12 `:227`. Each migration should stop caching failure as fact.
