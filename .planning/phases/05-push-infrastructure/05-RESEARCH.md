### Locked Decisions

**Notification content**
- Title format: Driver name + event summary (e.g., "Verstappen: Moved to P2")
- Body: Reuse the AI commentary snippet already generated by the backend commentary engine — no new text generation needed
- Tapping notification deep-links to the live timing tab

**Event triggering**
- Events that fire pushes: overtakes (top 10 only), safety car deployments, red flags, penalties, fastest lap changes
- Overtakes scope: any driver-to-driver position change in P1–P10 (not just favorite driver)
- Sessions: all live sessions — FP1, FP2, FP3, Qualifying, Sprint Qualifying, Sprint Race, Race

**APNs configuration**
- Auth method: Certificate-based (.p12) — no p8 key available

**Token management**
- Storage: PostgreSQL — add a `device_tokens` table to a new or existing Postgres instance
- Device identity: Pair token with a device UUID sent from iOS — one row per device, upsert on re-registration
- iOS re-registers token on every foreground activation

**Per-type opt-out**
- iOS app has a settings screen with toggles for each event type: overtakes, safety car, red flags, penalties, fastest lap
- Preferences stored on-device (UserDefaults) and sent to backend at registration time alongside the device token
- Backend filters which event types to push per device based on stored preferences

## Summary

This phase wires APNs push delivery for live F1 race events into the existing FastAPI + WebSocket backend already polling OpenF1 in `backend/app/api/routes.py`. The Phase 4 commentary engine already detects positional changes, safety car / VSC / red-flag transitions, and pit stops, and generates fan-friendly commentary text via Gemini. **Phase 5 piggybacks on that detection pipeline** — when a relevant event fires inside `live_timing()`, the same `_generate_commentary()` text is forwarded to APNs as the notification body. No new event-detection logic is required for overtakes, safety car, or red flags. **Penalties and fastest lap are NOT yet detected** in Phase 4 and require small additions to the existing event-detection layer (see Open Questions §Q1).

The recommended stack is aioapns 4.0 (last release April 2025, native asyncio, supports certificate auth), SQLAlchemy 2.0 async + asyncpg + Alembic for the new `device_tokens` table on Render's free PostgreSQL instance. Token registration is a single POST endpoint that upserts on `(device_uuid)`. iOS uses a minimal `UIApplicationDelegateAdaptor`-backed `AppDelegate` for `didRegisterForRemoteNotificationsWithDeviceToken`, plus a SwiftUI `ScenePhase` observer that re-POSTs the token on every `.active` transition. Sandbox vs production is selected from the existing `ENVIRONMENT` env var (already used by `logging_config.py` for structlog renderer selection per STATE.md decision 01-02), keeping configuration consistent.

**Primary recommendation:** Add `aioapns`, `sqlalchemy[asyncio]`, `asyncpg`, `alembic`, `cryptography` to `requirements.txt`; add a `app/data/device_tokens.py` module + Alembic migration; introduce `app/api/push.py` with two surfaces — a `POST /api/push/register` endpoint and a `dispatch_push_for_event(event, commentary_text, race_name)` async function called from the existing `live_timing()` WebSocket loop next to where `_generate_commentary` already runs.

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| aioapns | apns2 / PyAPNs2 | Synchronous; doesn't support Python 3.10+ (hyper dep dead). Not viable on this stack. [VERIFIED: WebSearch confirmed Python 3.10+ incompatibility in github.com/jazzband/django-push-notifications/issues/646] |
| aioapns | hyperapns / Pushy / APNS clients in other languages | Out of scope — backend is Python. |
| SQLAlchemy + asyncpg | Direct asyncpg + raw SQL | Simpler for one table, but loses migration tooling and forces hand-rolled query strings. Project has zero existing Postgres code; introducing the standard ORM stack now is cheaper than retrofitting later if the schema grows (preferences, opt-outs). |
| SQLAlchemy + asyncpg | SQLModel (Tiangolo's wrapper) | SQLModel is a thin layer over SQLAlchemy + Pydantic. Fine choice but adds a dependency for ergonomics; SQLAlchemy 2.0's typed `Mapped[T]` style already gives most of the same DX. Going with stock SQLAlchemy keeps the dependency tree leaner. |
| Alembic | Hand-written `CREATE TABLE` at startup | Works for one table but breaks down the moment the schema evolves. Alembic is the standard. |
| Render Postgres free tier | SQLite on Render persistent disk | SQLite on Render's ephemeral filesystem is the same problem already flagged for ChromaDB in STATE.md blockers. CONTEXT.md locks PostgreSQL. |
| Render Postgres free tier | Supabase / Neon | All work over `postgresql://` URL. Render is the existing host; staying inside Render avoids cross-provider latency and another secret. The 90-day expiration of Render's free Postgres is the only operational risk — see Open Questions §Q3. |

### Pattern 1: Lifespan-bound singletons (FastAPI startup)

**What:** Initialize the aioapns client and SQLAlchemy engine once during FastAPI startup, hold them in module-level singletons, tear down on shutdown.

**When to use:** All long-lived resources (DB engines, HTTP clients, APNs connections) MUST be created in the `lifespan` async context, not at request time. This matches the existing pattern from STATE.md decision 01-02 (ChromaDB singleton with double-check `threading.Lock`).

**Example:**

```python
# Source: https://fastapi.tiangolo.com/advanced/events/ + aioapns README
# backend/main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI
from app.services.apns_client import init_apns, close_apns
from app.data.db import init_db_engine, close_db_engine

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup
    await init_db_engine()
    init_apns()
    yield
    # shutdown
    await close_apns()
    await close_db_engine()

app = FastAPI(lifespan=lifespan)
```

### Pattern 2: aioapns certificate-based client (the core APNs surface)

**What:** Instantiate `aioapns.APNs` with a PEM cert path, fixed topic (bundle id), and sandbox flag.

**Example:**

```python
# Source: https://github.com/Fatal1ty/aioapns README
# backend/app/services/apns_client.py
from aioapns import APNs, NotificationRequest, PushType
from app.config import APNS_CERT_PATH, APNS_BUNDLE_ID, APNS_USE_SANDBOX

_client: APNs | None = None

def init_apns() -> None:
    global _client
    _client = APNs(
        client_cert=APNS_CERT_PATH,        # PEM file path
        topic=APNS_BUNDLE_ID,              # com.f1ai.app
        use_sandbox=APNS_USE_SANDBOX,      # True in dev, False in prod
    )

async def close_apns() -> None:
    # aioapns 4.x manages its own connection lifecycle; no explicit close needed
    # but keep the hook for future-proofing.
    pass

def get_apns() -> APNs:
    if _client is None:
        raise RuntimeError("APNs client not initialized — call init_apns() first")
    return _client
```

```python
from sqlalchemy import String, DateTime, Boolean, JSON
from sqlalchemy.orm import Mapped, mapped_column, DeclarativeBase
```

### Pattern 5: Postgres UPSERT for idempotent re-registration

**What:** iOS re-registers on every foreground; the same `(device_uuid)` should overwrite, not duplicate. Postgres `ON CONFLICT` is the canonical way.

**Example:**

```python
# Source: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#insert-on-conflict-upsert
async def upsert_token(session: AsyncSession, payload: RegisterTokenPayload) -> DeviceToken:
    stmt = pg_insert(DeviceToken).values(
        device_uuid=payload.device_uuid,
        apns_token=payload.apns_token,
        environment=payload.environment,
        enabled_event_types=payload.enabled_event_types,
        bundle_id=payload.bundle_id,
    ).on_conflict_do_update(
        index_elements=[DeviceToken.device_uuid],
        set_={
            "apns_token": payload.apns_token,
            "environment": payload.environment,
            "enabled_event_types": payload.enabled_event_types,
            "is_active": True,
            "updated_at": datetime.utcnow(),
        },
    ).returning(DeviceToken)
    result = await session.execute(stmt)
    return result.scalar_one()
```

### Pattern 6: iOS UIApplicationDelegateAdaptor for SwiftUI app lifecycle

**What:** SwiftUI's `App` protocol does not expose APNs callbacks; the supported pattern is to bridge a tiny `AppDelegate` via `@UIApplicationDelegateAdaptor`.

**Example:**

```swift
// Source: https://developer.apple.com/documentation/swiftui/uiapplicationdelegateadaptor
// + https://nilcoalescing.com/blog/RemotePushSetup/
// ios/F1AI/Services/AppDelegate.swift
import UIKit
import UserNotifications

final class AppDelegate: NSObject, UIApplicationDelegate, UNUserNotificationCenterDelegate {
    func application(_ application: UIApplication,
                     didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]? = nil) -> Bool {
        UNUserNotificationCenter.current().delegate = self
        return true
    }
```

### Pattern 7: Per-event-type rate limiting (Claude's discretion)

**What:** CONTEXT.md asks for per-event-type cooldowns so safety car and overtake don't suppress each other. The Phase 4 commentary engine has a single 30-sec global cooldown keyed by room (`COMMENTARY_COOLDOWN_SECONDS`). For pushes, separate cooldowns per `(room, event_type)`:

| Event type | Cooldown | Rationale |
|------------|----------|-----------|
| safety_car / vsc / red_flag | 60s | Status changes are rare and high-signal; one push per status transition is plenty |
| position_change (overtake P1–P10) | 15s | Overtakes cluster (especially at race start, after pit stops); 15s prevents spam without losing major moves |
| pit_stop | (NOT pushed in Phase 5 per CONTEXT.md) | — |
| fastest_lap | 30s | New fastest lap can trade hands during the same lap; 30s is enough to stabilize |
| penalty | 15s | Multiple penalties at once are rare; 15s prevents bursting |

Implementation: extend `_commentary_state[room]` dict to also key by event type:

```python
# backend/app/api/push.py
from time import time as now

PUSH_COOLDOWNS = {
    "safety_car": 60,
    "position_change": 15,
    "fastest_lap": 30,
    "penalty": 15,
}

_push_cooldown_state: dict[tuple[str, str], float] = {}

def should_push(room: str, event_type: str) -> bool:
    key = (room, event_type)
    cd = PUSH_COOLDOWNS.get(event_type, 30)
    last = _push_cooldown_state.get(key, 0.0)
    if now() - last >= cd:
        _push_cooldown_state[key] = now()
        return True
    return False
```

### Anti-Patterns to Avoid

- **Hand-rolling APNs HTTP/2 with raw `httpx`.** Apple changes the protocol details (priority semantics, `apns-push-type` requirements, JWT rotation if you switch to p8 later). aioapns absorbs all of that. Don't reinvent.
- **Storing the APNs token in Keychain on iOS, then reading it across launches.** Apple explicitly recommends NOT caching device tokens — re-request on every foreground. CONTEXT.md mandates this. Caching causes "stale token" bugs after iOS reissues.
- **Using a single `(token)` primary key.** Tokens rotate; users reinstall; the same physical device can produce multiple tokens. Pair with a stable `device_uuid` from the iOS Keychain (per `swift/security.md` use Keychain for the UUID).
- **Pushing from inside the request handler synchronously.** APNs round trips are tens of milliseconds × number of recipients. Always enqueue dispatch (`asyncio.create_task` or `BackgroundTasks`) so the WebSocket loop never blocks waiting for Apple.
- **Logging the full APNs token at INFO level.** Tokens are not secrets but are device-correlatable. Log only the last 8 chars (`token[-8:]`) at DEBUG.
- **Sending the same notification to all users, ignoring preferences.** Backend MUST filter by `enabled_event_types` per device per CONTEXT.md.
- **Calling `registerForRemoteNotifications()` before requesting permission**, or before the user has had a chance to accept. Permission must be granted (or at least requested) first; otherwise iOS silently does nothing.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| APNs HTTP/2 framing, JWT rotation, connection pooling | Custom `httpx`-based client | aioapns | Apple's protocol has dozens of edge cases (idle timeouts, reconnection on `GOAWAY`, channel concurrency limits, error codes shaped as JSON streams). aioapns implements them all. |
| Token expiry / inactive token cleanup | Sweep job that pings every token periodically | React to `Unregistered`/`BadDeviceToken` on send | APNs explicitly returns `410 Unregistered` when a token is inactive. The standard cleanup pattern is to delete on that response. A sweep job is cost-free in money but adds code paths and races. |
| .p12 → PEM conversion | Custom OpenSSL subprocess wrapper | `cryptography.hazmat.primitives.serialization.pkcs12.load_key_and_certificates` (in-process) OR pre-convert to PEM and store both as Render secrets | Subprocesses on Render free tier are fragile and add startup latency; in-process conversion or pre-converted secrets are safer. |
| Schema migrations | Hand-written `CREATE TABLE` strings on startup | Alembic | Migration tooling is the reason schema changes don't break in prod. |
| Async DB sessions | Manual asyncpg pool + raw SQL | SQLAlchemy 2.0 async + `AsyncSession` dependency | Session lifecycle, transaction boundaries, and connection pool tuning are deeply non-trivial. The dependency-injected `get_db()` pattern is the FastAPI standard. |
| Hex-encoding the device token from `Data` | Custom byte→string formatter that may produce uppercase or insert dashes | `deviceToken.map { String(format: "%02x", $0) }.joined()` (the documented one-liner) | APNs requires lowercase hex with no separators. Off-by-one casing breaks delivery silently. |
| Detecting iOS app foreground transitions | Notification observers (`UIApplication.didBecomeActiveNotification`) | SwiftUI `ScenePhase == .active` observer | `ScenePhase` is the modern SwiftUI API; works correctly with multi-scene + `UISceneDelegate` lifecycles. |

**Key insight:** APNs looks deceptively simple — "POST a JSON to Apple, done." The hard parts are HTTP/2 connection lifecycle, error stream parsing, certificate format conversion, and token lifecycle management. Every one of these is solved by aioapns + the `cryptography` package + the Postgres-backed token table. Hand-rolling any of them costs days and ships bugs.

## Common Pitfalls

### Pitfall 1: APNs environment mismatch

**What goes wrong:** Backend uses production gateway (`api.push.apple.com`) but the iOS device's token was issued by sandbox APNs (development build), or vice versa. APNs returns `400 BadDeviceToken` for every send, silently — no notification ever arrives.

**Why it happens:** The `aps-environment` entitlement embedded in the iOS app's signing profile determines which APNs server issues the token. Xcode debug builds use `development` (→ sandbox tokens). Ad Hoc / TestFlight / App Store builds use `production` (→ prod tokens). The backend has to match — sandbox cert + sandbox tokens go through `use_sandbox=True`; prod cert + prod tokens through `use_sandbox=False`.

**How to avoid:** Have iOS POST `environment: "sandbox" | "production"` along with the token (derived from the bundle's embedded provisioning profile, or from `#if DEBUG`). Backend stores it and uses the matching aioapns instance. Maintain TWO `aioapns.APNs` instances if the same backend serves both dev and prod clients; OR — simpler for portfolio scale — gate by `ENVIRONMENT` env var and accept that dev backend pushes only to dev devices.

**Warning signs:** Token registers fine, but no push arrives on the device. Server log shows `BadDeviceToken` with reason `BadDeviceToken`. [CITED: developer.apple.com/forums/thread/689857]

### Pitfall 2: aps-environment entitlement missing or wrong

**What goes wrong:** `application(_:didFailToRegisterForRemoteNotificationsWithError:)` fires with "no valid 'aps-environment' entitlement string found for application." The device never gets a token at all.

**Why it happens:** The `aps-environment` key must be in the `.entitlements` file AND the signing profile must include the Push Notifications capability. xcodegen's `project.yml` doesn't yet declare an entitlements file for F1AI.

**How to avoid:**
1. Create `ios/F1AI/F1AI.entitlements` with `<key>aps-environment</key><string>development</string>`.
2. Add `CODE_SIGN_ENTITLEMENTS: F1AI/F1AI.entitlements` to `project.yml` `targets.F1AI.settings.base`.
3. Enable Push Notifications capability in Apple Developer Portal under the App ID `com.f1ai.app`.
4. Regenerate provisioning profile.

**Warning signs:** `didFailToRegisterForRemoteNotificationsWithError` log; Xcode console error mentions entitlement.

### Pitfall 3: Infinite loop on Render free tier when device-token table is empty

**What goes wrong:** First-time deploy with no registered devices — every event in `live_timing()` triggers a send loop with zero recipients. Harmless but logs noise; if a bug makes the query slow, it amplifies.

**How to avoid:** Short-circuit `dispatch_push_for_event()` when `tokens_for_event_type()` returns empty. Log at DEBUG, not INFO.

**Warning signs:** N/A (this is a code-cleanliness pitfall, not a runtime bug).

### Pitfall 4: Render free Postgres 90-day expiration

**What goes wrong:** Render's free PostgreSQL instance expires after 90 days. The backend starts returning DB connection errors; pushes silently stop because token registration fails.

**How to avoid:** Document the renewal cadence; or upgrade to paid Render Postgres ($7/month at time of writing) when the project moves past pure-portfolio. Add a startup health check that pings the DB and surfaces an error log if it fails. [VERIFIED via WebSearch: render.com free tier docs confirm 90-day Postgres expiration; [CITED: render.com/docs/databases]]

**Warning signs:** Logs show `asyncpg.exceptions.ConnectionFailureError` after long uptime. Token registration endpoint returns 500.

### Pitfall 5: blocking the WebSocket loop on slow APNs sends

**What goes wrong:** A single `await get_apns().send_notification(req)` takes 50–200 ms. If 100 devices are registered and you await each in series inside the WebSocket loop, the loop pauses for 5–20 seconds between OpenF1 polls. Position updates stall.

**How to avoid:** Fan out via `asyncio.gather(*[send(t) for t in tokens])` (aioapns is HTTP/2 multiplexed — concurrent sends are cheap), OR offload the entire `dispatch_push_for_event` to an `asyncio.create_task(...)` so the WebSocket loop continues immediately. The latter is simpler and correct for portfolio scale.

**Warning signs:** WebSocket clients see `positions` updates lag during heavy event bursts; Render logs show `WS_POLL_INTERVAL` (8s) drifting upward.

### Pitfall 6: iOS `registerForRemoteNotifications` on every foreground = potential rate-limit log spam

**What goes wrong:** iOS allows `registerForRemoteNotifications` to be called many times per session — but every call hits the OS, which talks to Apple — so calling it dozens of times per minute (e.g., on a tight `ScenePhase` watcher) is wasteful. The bigger issue: every call POSTs to the backend, which is fine but wastes battery and network.

**How to avoid:** Debounce: only re-register if at least N seconds have passed since the last registration POST, OR if the token actually changed (compare against last-sent token in memory — note: NOT cached across launches per Apple's guidance).

**Warning signs:** Backend logs show duplicate registrations every few seconds.

### Pitfall 7: didReceiveRemoteNotification UI updates from background thread

**What goes wrong:** The `UNUserNotificationCenterDelegate` callbacks run on a background thread. Mutating `@State` or `@Published` properties from there crashes or fails silently in Swift 6 strict concurrency.

**How to avoid:** Wrap UI updates in `await MainActor.run { ... }` or annotate the receiver class `@MainActor`.

**Warning signs:** Tap-to-deep-link doesn't navigate; or runtime warning about main thread checker.

### Pitfall 8: APNs payload size > 4 KB

**What goes wrong:** Apple rejects payloads >4 KB for alert pushes (5 KB for VoIP). Reusing Phase 4 commentary text could exceed this if the LLM verboses out.

**How to avoid:** Truncate the body to ~200 chars before stuffing into APNs payload. The body is shown on the lock screen; iOS truncates anyway.

**Warning signs:** `PayloadTooLarge` error response.

### Dispatch on event detection (PUSH-02)

```python
# backend/app/api/push.py (continued)
import asyncio
from aioapns import NotificationRequest, PushType
from app.services.apns_client import get_apns
from app.data.device_tokens import tokens_for_event_type, deactivate_token

async def dispatch_push_for_event(
    room: str,
    event_type: str,
    title: str,
    body: str,
    session: AsyncSession,
) -> None:
    if not should_push(room, event_type):
        return

    tokens = await tokens_for_event_type(session, event_type)
    if not tokens:
        return

    payload = {
        "aps": {
            "alert": {"title": title, "body": body[:200]},
            "sound": "default",
            "badge": 1,
            "thread-id": "live-race-events",
        },
        "deep_link": "f1ai://live",
        "event_type": event_type,
    }

    async def _send_one(t: DeviceToken) -> None:
        req = NotificationRequest(
            device_token=t.apns_token,
            message=payload,
            push_type=PushType.ALERT,
            time_to_live=300,
        )
        try:
            res = await get_apns().send_notification(req)
            if not res.is_successful:
                if res.description in {"Unregistered", "BadDeviceToken"}:
                    await deactivate_token(session, t.device_uuid)
        except Exception as e:
            logger.warning("apns.send_failed", token=t.apns_token[-8:], error=str(e))

    await asyncio.gather(*[_send_one(t) for t in tokens])
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `apns2` / `PyAPNs2` (sync, hyper-based) | `aioapns` 4.x (async, httpx/h2-based) | Python 3.10 dropped `hyper` compat (2021–2022 era) | Sync APNs libraries are dead for modern Python; aioapns is the only well-maintained choice. |
| Binary APNs protocol on port 2195 | HTTP/2 protocol on port 443 (or 2197) | Apple deprecated binary protocol Nov 2020 | All current libraries use HTTP/2; this is settled. |
| AppDelegate-only SwiftUI apps | `@UIApplicationDelegateAdaptor` bridge in App protocol | iOS 14 / SwiftUI 2.0 | Bridge is the documented pattern; pure-AppDelegate is legacy. |
| .p12 certificates with annual renewal | .p8 token-based auth (no expiry, supports multiple bundle IDs) | Apple introduced JWT-based auth around 2016 | CONTEXT.md locks .p12, so this is informational — but if a .p8 becomes available later, aioapns supports it identically (`key=`, `key_id=`, `team_id=`, `topic=`). |
| SQLAlchemy 1.x `Query` API | SQLAlchemy 2.0 `select()` + typed `Mapped[T]` | 2.0 release Jan 2023 | All new code should use 2.0 style; legacy `Query` still works but is deprecated for new projects. |

**Deprecated/outdated:**
- `hyper` HTTP/2 lib — abandoned, dropped Python 3.10 support.
- APNs binary protocol — Apple disabled Nov 2020.
- Storing device tokens client-side and reusing across launches — Apple guidance is to re-fetch on every foreground.

## Open Questions

1. **Penalty and fastest-lap event detection are NOT yet built in Phase 4 — what data sources back them?**
   - What we know: Phase 4 `_detect_event` handles safety_car, position_change, pit_stop. CONTEXT.md PUSH-02 requires penalties + fastest_lap.
   - What's unclear: OpenF1 has `/v1/race_control` which Phase 4 already consults for safety car / red flag (Phase 4 keys off the `flag` field). Penalties usually appear here as `category=OTHER` with messages like "PENALTY FOR CAR 11 - 5 SECOND TIME PENALTY". OpenF1 `/v1/laps` includes `lap_duration` per driver per lap — fastest lap can be derived by tracking the minimum across the session.
   - Recommendation: Plan must include a small extension to `_detect_event()` to handle these two new types. Either dedicate a wave to extending Phase 4's event detector, or accept that fastest_lap detection is best-effort if OpenF1 lap data lags. **Confirm with user during plan-check whether penalties are scope for Phase 5 or deferred** — CONTEXT.md says yes, but the implementation cost is meaningful.

2. **How is the .p12 certificate delivered to the Render runtime filesystem?**
   - What we know: Render's free tier does not include persistent disk; `render.yaml` env vars are strings only.
   - What's unclear: Three options exist: (a) base64-encode the .p12 into an env var, decode at startup to a temp file; (b) commit an encrypted blob to git; (c) upgrade to a paid disk. The pattern is operationally common (Heroku uses the same approach) and (a) is the most portable.
   - Recommendation: Plan should add a startup helper (`backend/app/services/apns_client.py: _materialize_cert()`) that reads `APNS_CERT_B64` env var and writes the decoded PEM to `/tmp/apns-cert.pem` on first call. Alternatively pre-convert .p12 to PEM locally and base64 the PEM file (smaller, no password handling needed at runtime).

3. **Does the user already have a Render Postgres instance, or is this Phase 5 the first?**
   - What we know: STATE.md Blockers mentions "Render.com free tier: ChromaDB on ephemeral storage" — so currently no Postgres. `render.yaml` has no `databases:` block.
   - What's unclear: Whether the user has provisioned a Postgres elsewhere (Supabase, Neon, local) that they'd prefer to point at.
   - Recommendation: Plan should include a step to add `databases:` to `render.yaml`, but document the URL-only environment so any provider works.

4. **How does the iOS app detect "current environment" for the `environment` field in registration?**
   - What we know: `#if DEBUG` works for "is this Xcode debug build" but not for distinguishing TestFlight (production APNs) from App Store (also production APNs). Both are production for the purposes of this phase.
   - What's unclear: Edge case is sideloaded Ad-Hoc builds — they use production APNs but should match a backend that's running in production mode.
   - Recommendation: Use `#if DEBUG` for now. If the project grows to TestFlight distribution in the same backend serving prod, revisit by reading the embedded provisioning profile's `aps-environment` value at runtime (a 30-line helper).

5. **Is there an iOS app delegate already?**
   - What we know: `F1AIApp.swift` is pure-SwiftUI with no `UIApplicationDelegateAdaptor`. The app uses `LiveActivityService` (Phase 4) which is plain Swift, no delegate needed.
   - What's unclear: Nothing — Phase 5 introduces the AppDelegate.
   - Recommendation: New file `ios/F1AI/Services/AppDelegate.swift`; tiny, single responsibility, conforms to UIApplicationDelegate + UNUserNotificationCenterDelegate.

6. **Should the registration endpoint also include the device's APNs environment in the URL or body?**
   - What we know: CONTEXT.md doesn't specify, but the environment is critical for matching at send time (Pitfall 1).
   - What's unclear: Whether multiple environments should ever coexist in the same DB row.
   - Recommendation: Body field per the schema in §Pattern 4. One row per device_uuid; environment column updated on re-register.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | partial | No user auth in this app (single-user portfolio per STATE.md). Device registration is unauthenticated by design — anyone with the URL can POST a token. Acceptable for portfolio scale; if scaled, add a per-device shared secret. |
| V3 Session Management | no | Stateless REST + WebSocket. No sessions. |
| V4 Access Control | no | No multi-tenant logic in v1. |
| V5 Input Validation | yes | Pydantic models with strict regex on token (`^[a-f0-9]+$`, 64–200 chars), bundle id format, environment enum. Reject malformed at the boundary. |
| V6 Cryptography | yes | TLS to APNs via aioapns (HTTP/2 over TLS). Keychain on iOS for the device UUID. Never log full APNs token (Pitfall 5). The .p12 cert is a secret — see §V14. |
| V7 Error Handling | yes | structlog already in use; APNs errors logged with truncated tokens. Don't leak stack traces from `/api/push/register`. |
| V14 Configuration | yes | Cert delivered via env-based secret (Render env var, base64-encoded), not committed. `APNS_CERT_PASSWORD` if .p12 has a password — env var only. |

### Known Threat Patterns for FastAPI + APNs + iOS stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token enumeration / device spoofing (attacker registers fake `device_uuid` to receive someone else's pushes) | Spoofing | Pushes contain only public race events — no PII. Even if an attacker registers a token, they receive the same content as everyone else. Acceptable for this domain. |
| Spam registration (attacker floods `/api/push/register`) | DoS | Add IP-based rate limiting via `slowapi` or Render's built-in DDoS protection. Cap rows per IP. |
| Cert leakage (.p12 in repo or logs) | Information Disclosure | Pre-commit hooks scanning for `.p12`/`.pem` files; never log cert path; never commit `secrets/` directory. Add `*.p12`, `*.pem`, `*.p8` to `.gitignore`. |
| Device token exfiltration (DB compromise) | Information Disclosure | Tokens are not user-identifying alone, but combined with pushes can fingerprint. Encrypt at rest is overkill; standard Postgres TLS (Render default) is sufficient for portfolio. |
| Man-in-the-middle on registration POST | Tampering | HTTPS required for production; reject HTTP in production env (`fastapi.middleware.https_redirect.HTTPSRedirectMiddleware` if not handled by Render's edge). |
| Replay attacks on push send | Tampering | aioapns sets `apns-id` per request; APNs deduplicates within a 24-hour window. No additional control needed. |
| Malicious deep-link payload (attacker-controlled push?) | Tampering / Elevation | Backend is the only sender. iOS validates `userInfo["deep_link"]` is a known scheme before navigating. Don't pass arbitrary URLs into `WebView` or `openURL`. |
